An undo button for AI agents.

Backstep sits between an AI agent and the tools it calls. Before the agent changes any data, it records what that data looked like, so any mistake can be reviewed and rolled back with one command.

The problem

Agents can change real data now. They still make mistakes.

Agents have write access.

They run queries against real databases, file stores and cloud accounts.

They still get it wrong.

An UPDATE with the wrong WHERE clause. An insert loop that runs 200 times.

Two bad options.

Keep the agent read-only, or give it write access and hope for the best.

The third option

Let the agent act, keep an exact record of every change, and undo any of it with one command.

How it works

Five steps, on every tool call.

  1. 1

    Intercept

    Every tool call the agent makes passes through Backstep first.

    Technical detail

    A transparent MCP proxy aggregates tools from every configured upstream server and routes each call through an interceptor. It never alters or swallows the upstream response.

  2. 2

    Classify

    Each tool has a risk grade, from read-only to irreversible.

    Technical detail

    Looks up the tool's reversibility class (R0 to R4) and decides to pass it through, journal it, ask for confirmation or block it. No model is in the loop at runtime.

  3. 3

    Capture

    Before anything changes, it saves a copy of the rows about to change.

    Technical detail

    The Postgres adapter parses the statement with sqlglot, rewrites the INSERT, UPDATE or DELETE into a SELECT over the same rows, and runs it on its own connection.

  4. 4

    Journal

    It writes down what happened and what the data looked like before.

    Technical detail

    An append-only SQLite journal stores the call's arguments, the state before the change and a fingerprint of the state right after it.

  5. 5

    Revert

    One command puts it back. If someone else has changed the data since, it stops.

    Technical detail

    Compares the live rows with the stored fingerprint. No drift: restore the original rows. Any drift: refuse and show the difference.

Not every action can be undone. Backstep knows which.

Every tool gets a reversibility grade. It decides what is recorded, what needs your confirmation and what is refused.

Why a refusal is a pass

In partial_drift, reverting would have destroyed someone else's edit. In unparseable_sql, Backstep could not safely read the statement, so it declined to guess.

The honest partial

In cascading_delete, Postgres removes child rows inside the same statement, before Backstep can see them. The parents come back; the children do not.

Engineering approach

A safety tool has to be trustworthy itself.

Getting started

Four commands.

Install with uv, then point your MCP client at the proxy instead of the upstream server.

terminal 
$ uv sync                 # install dependencies
$ uv run backstep init    # optional: Claude grades each tool
$ uv run backstep doctor  # check config, journal, database
$ uv run backstep serve   # run the proxy

First copy backstep.example.toml to backstep.toml and add your upstream server and Postgres connection string. init needs ANTHROPIC_API_KEY.
